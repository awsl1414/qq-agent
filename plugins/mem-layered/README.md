# 分层记忆（增强版） · mem-layered

一个不碰宿主代码的长时记忆插件，通过 hooks 与能力名挂进 QQ Agent。
能力名与内置记忆模块完全一致（`memory.search` / `memory.archive` / `memory.status` / `memory.rebuild`），
所以宿主的 `skills/memory-recall/` 与数据移植模块不用改一行就能复用本引擎。

```bash
node tools/selftest.mjs     # 173 项断言，离线可跑，不需要宿主、不需要联网
```

当前版本 v1.7.1。版本演进记录见 `CHANGELOG.md`，本页只讲它现在怎么工作。

## 四个记忆机制

这四个机制都在人类记忆实验里有对应物。插件不猜情绪、不做情感分析，只认时间和共现
（N7 组断言守住这条边界）。

**共激活联想**（Hebb：一起激活的连在一起）。同一轮主动检索里一起被想起的块互相结缘
（links 计数，邻居 ≤12、计数 ≤20 双封顶），之后检索时激活向邻居扩散。
与 top 命中结缘的块加分，字面零匹配但当时一起想到的块也会被带出来；
种子分只借 12%，永远排在真命中后面，自动注入的相关度早停会滤掉它。
结缘只在模型主动检索时发生，被动注入是"被看到"，不算"一起想到"。

**自发恢复**（Humphreys 痕迹复苏）。保持率不再单调下降。块进入深忘区（距上次命中 > 3S）
后，在纯衰减之上叠一个自己也衰减的小回升，形状是"沉下去、弹一下、归于没有"。
幅度按淘汰阈值的 40% 自动封顶，所以弹得再高终会落到淘汰线以下，库不会只进不出
（N3 有终局断言）。

**时段情境**（编码特异性的另一条线索）。同一时段发生的事，在当下这个时段更容易被提取，
默认 ×1.1。这与问句里显式提到"晚上"是两回事。

**睡眠重演**。插件按最优难度区间（距上次命中 ≈ 该块半衰期、有效权重 0.5~0.95、冷却 ≥3 天）
挑一块，下次激活时以【突然想起】带出一句。它不看你问什么，只看这块该复习了。
一次最多一块，字符预算另算，护栏降档时自动停播，与"相关旧事"共用冷却去重，
播出后按 full 计权（测试效应）。`sleepReplay` 可以关掉。

### 记忆强度模型（v1.4.0 起，对齐人类记忆的四个实测性质）

```
effectiveScore = clamp(score, 0.05, 3) × 0.5^((距上次命中天数 / S)^q)      q = decayShape，默认 0.7
r              = min(4, log2(1 + 间隔天数 / S))
score          = clamp(score × (1 + (hitBoost - 1) × r), 0.05, 3)
S              = clamp(S × (1 + stabilityGain × r), 1, stabilityMax)
```

| 人类记忆的性质 | 模型里对应什么 | 旧行为 |
|---|---|---|
| **间隔重复效应**：隔久了再想起来，比一分钟内连想八遍记得牢 | 增益 `r` 是间隔的增函数。间隔 ≈ 0 时 `r ≈ 0` → **几乎不加分**；间隔 = S 时增益恰好是 `hitBoost` | 固定 ×`hitBoost`，与间隔无关 |
| **稳定性随提取增长**：反复成功回忆的东西，衰减本身就变慢 | 每块有自己的 `S`（天），命中后按 `r` 增长。间隔 ≪ S 时每次约 +1.44×间隔 天 | 所有块共用一个全局半衰期 |
| **遗忘曲线是长尾不是纯指数** | `q = 0.7`：早期掉得更快、后面拖一条长尾。`q = 1` 可退回纯指数 | `0.5^(t/半衰期)` |
| **测试效应**：主动回忆 ≫ 被动重看 | **被动注入一个字节都不改**，只记 `passiveHits` 计数；只有模型主动调检索工具才计权 | 每轮自动注入也在加分，形成"越注入越强 → 越强越注入"的正反馈 |

被动计权为什么不能"只刷新锚点"：锚点一刷新，`effectiveScore ≈ score ≈ 1` 永远高于淘汰阈值，
于是**凡是被自动注入过的块全都长生不老**，库无限膨胀。人的"眼熟"确实存在，
但它换来的是识别不是回忆，工程上不该拿权重表达。

配套的 `feedback` 三态：`'full'`（主动检索，默认）/ `'passive'`（只记计数）/ `'off'`（纯查询）。
每轮自动注入走的是 `'off'` —— 正反馈环在**两个地方**同时被掐断。

改动的实际效果（8 次命中，`hitBoost=1.15`）：

| 命中方式 | 稳定性 S | score | 含义 |
|---|---|---|---|
| 同一瞬间连打 8 次 | 45 天（不涨） | 1.00（不加） | 旧行为下这两个数字是 **3.0 / 8 次封顶** |
| 每 30 天一次 × 8 次 | **356 天（7.9×）** | 1.43 | 间隔命中把"记得牢"真的记下来了 |

用 `tools/curve-sim.html` 可以自己拉参数看：把 `stabilityGain` 拉到 0，「间隔 vs 密集」立刻退回 1×。

### 梗概墓碑（v1.5.0 起，模糊痕迹理论 + 节省效应）

```
淘汰块时：  压一条 ≤40 字要旨（谁 + 主题词 + 大意）+ 关键词 + id 区间 → gist.json
检索时：    墓碑作为**低权重候选**参与同一轮排序（默认 ×0.35）
命中时：    按 minId/maxId 从 messages/ 捞回那一段 → 重建块 → 摘掉墓碑
```

| 人类记忆的性质 | 模型里对应什么 |
|---|---|
| **模糊痕迹理论**：记忆同时存逐字痕迹与要旨痕迹，逐字的先烂 | 要旨刻意不带时间、不带原话 —— 那些本来就该烂掉；留的是"谁 + 干什么 + 主题词"的骨架 |
| **节省效应**：即使完全想不起来，重新学习也比第一次快得多 | 块只是 `messages/` 的索引视图，`messages/` 是只读完整真相源。所以"删块"从来没真的丢数据，丢的是"知道去哪儿找" —— 墓碑补的就是这一条线索 |
| **墓碑也要会忘** | 每会话上限 `gistMaxPerChat`（默认 400 条）+ 保留期 `gistRetainDays`（默认 3 年），超了从最老的开始丢 |

墓碑为什么可以活得比块久得多：**一条只有几十字节，块文件是几 KB 起**。
用极小的体积换"我好像记得有这么回事"，这是本插件性价比最高的一处设计。

⚠️ 权重刻意压到 0.35 倍：活块匹配得一样好时永远排在前面，墓碑只在
"没有活块能回答"时才浮上来。命中后如果能重建就给全文，重建不了（会话文件超过
`gistReviveMaxMb`）就退化成只给一句要旨 —— 同步 `JSON.parse` 一个几十 MB 的文件
足以把 5 秒钩子预算里的这一轮对话拖垮，所以这条守卫是硬的。

### 多线索检索（v1.5.0 起，编码特异性）

**认知心理学的编码特异性原理**：提取时的线索与编码时的线索越接近，越容易想起来。
人回忆旧事时，"当时谁在场"往往比"当时聊了啥词"更有效 ——
你会因为看到老朋友而想起十年前那件事，而不是因为想到了那句话。

工程对应：块里"在场的人"（uid 集合）与触发消息里"在场的人"有交集 →
该块加权 `peopleBoost`（默认 1.3，填 1 = 关闭）。

两个必须注意的细节：

- **按 uid 匹配，不是按昵称**。昵称会改，uid 不会。否则同一个人在块里叫"阿甲"、
  在触发消息里叫"阿甲（新）"，就永远对不上。
- **机器人自己不算"在场的人"**。它几乎每轮都在，算进去的话
  "在场的人有交集"会退化成"块里有人说过话"，加权等于没加。

墓碑上也记了 `people`，所以块被淘汰之后这条线索不会断。

### 检索结果多样性（v1.5.0 起，干扰理论）

**认知心理学的干扰理论**：相似的记忆会互相干扰 —— 想起一件就会压住另一件。
不处理的话，自动注入的前几条常常是相邻几个小时的同一段对话，
看着像想起两件事，其实是一件。

工程对应：贪心 MMR。每条候选按 `(1−λ) × 相关度 − λ × 与已选条目的内容重叠度`
挑选，`λ = diversityLambda`（默认 0.3，填 0 = 关闭，退回纯按分数取前 N）。

重叠度按**块关键词的 Jaccard** 算，读的是索引元数据里的 `kw` 指纹，
**不读块文件** —— 为了算相似度给每次命中挂一次 IO 不划算。

⚠️ 纯 Jaccard 會被"讨论/事情/相关"这类**通用词**骗到：两个毫无关系的块
因为都说了"讨论"就算出高重叠。所以重叠度按**词频加权**的 Jaccard 算
（交集取 `min`、并集取 `max` 频次），只认"某个词在这个块里被反复提起"。
这条一开始写错过，是 K/L 组断言抓出来的。

### 刻意不做：不猜情绪

碎片权重 `weightOf` 只认可判定的结构信号：

| 信号 | 说明 |
|---|---|
| 长度 ≥ 12 字 | 信息量 |
| 提问 / 约定 / 链接 / "怎么/为什么/明天/记得" | 可执行内容 |
| `[合并转发 共 N]` | 成块的信源 |
| 自己说的（`self`） | 略加权 0.2 |
| ≤ 2 字 | 衰减 0.4 倍 |

**没有**感叹号密度、**没有**人称密度、**没有**情感分析、**没有**"重要度"打分。
理由很简单：靠启发式判断"这句话更激动、更重要"就会悄悄改变整套记忆的取舍，
而寒暄与日常恰恰是记忆的主体。宁可平淡，也要可预测。
（J9 / L3 两条**反向断言**守着这条边界 —— 谁想把启发式加回来，测试先红。）

### 省 token（v1.6.0 起）

同一个目标：**命中率不掉，字符变少**。三条防线各管一段，都不裁新内容：

| 防线 | 省的是什么 | 为什么不会掉命中 |
|---|---|---|
| 碎片级跨轮去重 `staleSnippetSkip` | 上轮已经注入过的**原话**（按消息 `mid` 判身份） | 重复的原话对模型没有新信息；它只会挤占真正的新内容 |
| 相关度早停 `autoRecallMinRel` | 归一化相关度 < 最高分 25% 的候选块 | 低分块对回答的贡献极小；而"最强的那个块永远保留" |
| 预算行宽联动 | 预算内改摊行宽，不再"1 条长的 + 2 条被整条砍掉" | 同样字符覆盖更多条旧事，信息面反而更宽 |

**两个刻意的设计取舍：**

- **早停只作用于自动注入**。模型主动调 `memory.search` 时一条都不裁 ——
  那是它明确要"翻一下"，跟被动塞给它是两回事（M4 有一条断言钉住这个区别）。
- **`lastMids` 只记"真的写进提示词的那些行"**。预算裁掉的行模型根本没看到，
  把它算成"给过了"，下一轮该给的也不给 —— 白丢命中（M5 钉住）。

**实测**：3 个小时块 × 4 条约 40 字的同一话题，连跑 6 轮注入，
**1188 → 792 字符（−33%）**，注入次数一条没少。M8 断言固化方向而非数字。

**可观测**：`memory.status` 新增 `skippedStale`（跳过的旧碎片）、
`skippedLowScore`（早停丢掉的候选）、`autoInjectSkipAll`（整段省掉的次数）、
`linesPerInject` / `charsPerLine`。省了多少、省在哪儿，一眼能看到。

## 安装

1. 把整个 `mem-layered/` 目录放进宿主的插件目录：

   ```
   <项目根>/plugins/mem-layered/
   ```

2. **点一次「信任」**。插件需要 `fs`，会被静态准入闸按"触碰了高危能力"拦下，
   这是设计如此（插件与主进程同进程运行，导入 fs 等于拿到本机权限）。
   在插件页对应卡片上点「信任并继续」，或手工把目录名写进配置：

   ```json
   { "trustedPlugins": ["mem-layered"] }
   ```

   ⚠️ 登记的是**目录名**，不是清单里的 id。

3. **关掉内置的 `分层会话记忆`**（插件页的开关）。**这一步不能省**，理由三条，
   全部来自宿主源码：

   | 层面 | 两个都开时会发生什么 | 依据 |
   |---|---|---|
   | 钩子 | **注入会叠加**。`runHook` 是"遍历所有已激活 Skill 依次调用"，不是竞争 —— 两个 `before-llm-messages` 都会跑，而且**都往最后一条 user 消息的末尾追加**（内置版的函数名叫 `appendToSystem`，实际找的是 `role === 'user'`）。结果是同一轮提示词里挂两段记忆：内容重复、token 翻倍。不报错、不崩，只是钱和注意力被浪费一半 | `src/skills/manager.js` 的 `runHook` |
   | 能力 | **模型主动检索会走内置版**。两者都提供 `memory.search` 等四个能力，而 `CapabilityRegistry.providersOf` 按**注册顺序**返回、`api.capability()` 的注释明说"只取第一个生效的提供者"。注册顺序 = `readdirSync(plugins/)` 的字母序，`conversation-memory`（c）排在 `mem-layered`（m）**前面** → 内置版赢。不报错，只是"装了新引擎、模型查的还是旧数据" | `src/skills/capabilities.js` + `plugin-loader.js` |
   | 定时器 | 两份后台巩固同时在跑（内置 8 秒首跑、本插件 10 秒首跑，之后各 10 分钟一次）。都只读 `messages/`、各写各自的数据根，所以**不互相破坏**，只是 CPU 与磁盘 IO 双份 | 两个 `activate()` |

   **不会冲突的部分**：数据根完全隔离（内置写 `memory-v2/`，本插件写 `memory-v3/`）；
   工具 id 会按 `${skillId}__${toolId}` 前缀化，不会重名；`plugin-data/<skillId>/` 按 id 分目录；
   `/api/memory-files`（群友印象）属于核心 `MemoryStore`，两边都碰不到。

   关掉内置版后它的 `isActive` 变 false → 钩子不跑、能力也不算生效，本插件成为唯一提供者，
   `memory_search` 就会走本引擎。内置版的数据留在 `memory-v2/` 里不删。

   ⚠️ 顺带说明：**不需要迁移数据**。原始聊天记录 `data/messages/` 是唯一真相源且只读，
   本插件跑一轮巩固就能把历史全部重建出来 —— 这也是"块可以放心淘汰"的前提。

   ✅ **忘了关也不要紧**：本插件在启用时会自己检测内置版是否还开着，并主动提醒你
   （日志一条 + `memory_status` 里一条 + 私聊里一句话，见下面「冲突自检」）。

4. 不用手工重启：`plugin-loader` 用 `fs.watch` 监听插件目录，改完约 2 秒自动热重载。

### 冲突自检（`lib/conflict.js`）

上面那三条理由写在文档里，但**文档不会主动找你**。所以插件自己会查、会提醒。
宿主没给插件"读别的 Skill 配置"或"列出能力提供者"的接口
（`createSkillApi` 的白名单只有 `isSkillActive` / `capability` / `hasCapability`），
所以只用两件事拼出结论，全程不碰宿主一个字节：

| 问什么 | 怎么问 | 得到什么 |
|---|---|---|
| 内置版还开着吗 | `api.isSkillActive('conversation-memory')` | 纯内存查询，无 IO |
| 能力被谁抢走了 | 调 `api.capability('memory.status', {探针})`，看**第一个**提供者回不回本插件的引擎标记 `engine: 'mem-layered'` | 回了 = 我排在前面；没回 = 内置版赢 |

探针在**本插件自己的** provider 里短路返回 —— 不建实例、不读盘、不算体积
（它是在 `activate()` 里跑的，多一次磁盘遍历就是白等）。内置版不认识这个参数，
会照常算它自己的状态（几个内存计数，代价极小）。**只有内置版确实生效时才会去探针**，
没冲突就不花这一分钱。

三级结论：

| level | 含义 | 提醒文案强调什么 |
|---|---|---|
| `none` | 内置版没生效 —— 什么都没发生 | 不提醒 |
| `duplicate` | 内置版开着，但第一个提供者仍是本插件 | 重复注入 + 双份 token + 双定时器 |
| `shadowed` | 内置版开着**且抢走了能力**（默认情形，字母序决定） | 上面全部，外加"模型主动检索查到的是它的旧数据" |

探针问不出来时（没提供者 / 抛错）**按较轻的 `duplicate` 报，不夸大**。

提醒走三条路，都受 `warnOnConflict` 开关控制：

1. **日志**：`activate()` 时 `api.warn()` 一条完整说明（启动 / 热重载 / 手动开都跑一次，
   `force: true` 复查，所以你把内置版关掉后结论会立刻跟上）。
2. **状态**：`memory.status` 返回里多一个 `conflict` 字段（含 `level` / `builtinActive` /
   `selfFirst` / `hint`），宿主自带的 `memory_status` 工具一查就能看到。
3. **私聊里的一句话**：注入一行极短的提醒，让模型顺口转达。

关于第 3 条的几个刻意设计：

- **只在私聊**（`chatKey` 以 `private:` 开头）。群聊里播报插件配置，等于当着陌生人的面
  念主人的设置页 —— 这是安全默认，**不做成开关**。
- **默认一天一次**（`conflictWarnCooldownMin`，1440 分钟），冷却记在宿主给的
  `plugin-data/mem-layered/storage.json` 里，**重启 / 热重载不会重新计时**。
- **只有真的注进去了才记账**：找不到 user 消息时 `appendToLastUser` 返回 false，
  这次冷却不会被白吃掉。
- **不进成本护栏的裁剪**：它只有一行，而且它是配置问题，跟"这轮省不省 token"不是一回事。
- 文案末尾明确写着"说一次就够，别反复念叨"，免得模型每轮都念。

## 数据落点

全部收在自己的数据根里，卸载 = 删一个目录（内置版把 `cost-guard.json`、
`pending-todos.json`、`semantic-cards/` 散在 `data/` 根，卸载后留一地文件）。

```
<DATA_DIR>/memory-v3/
├── index/<会话>.json     倒排索引（按会话分片）
├── blocks/<块id>.json    小时块 / 日块
├── state.json            巩固游标 + 块权重（水位线、回填标记、score/hits/S）
├── stats.json            效果度量
├── gist.json             梗概墓碑（被淘汰的块留下的线索，几十字节/条）
├── cards.json            语义卡
├── todos.json            待办
├── cross-turn/<会话>.json 跨轮工作记忆
└── budget.json           成本护栏计数
```

**原始聊天记录 `<DATA_DIR>/messages/` 是唯一真相源，本插件只读、永不改写。**

唯一一处例外是**冲突提醒的冷却时间戳**：它走宿主给插件自己的存储
`<DATA_DIR>/plugin-data/mem-layered/storage.json`，只存一个 `{ at, level }`。
这么放是为了让"重启 / 热重载不重新计时"，卸载时连这个目录一起删掉即可。

## 几个容易踩的点

**注入为什么必须放在最后一条 user 消息末尾？**
`system` 是整条请求前缀的第一段，它尾巴一变，后面的 `tools` 与整条 `user` 全部缓存失效。
内置版踩过这个坑（真实调用第 1 次只命中 2560 tok，第 2 次才 98%）。
而 `user` 消息的**尾部**本来就是易变段（【此刻状态】【当前时间】每次运行都不同），
把注入放这里不额外增加任何缓存损失。

**为什么钩子里不跑巩固？**
所有 hook 有 5000ms 超时。巩固要读文件、写索引、重排倒排 —— 超时会被整个跳过，
还可能留下半截状态。巩固只交给 `activate()` 里的定时器。

**成本护栏为什么只接受"本轮增量"？**
宿主 `after-response` **每轮**都会触发，而 `ctx.session.usage` 是**运行级累计值**。
若上报累计值，一轮两次调用会被记成 23K + 47K = 70K（实际 47K）——
内置版踩过这个坑，真实 791K 被记成 1285K（×1.62）。所以只读 `ctx.response.usage`。

**`cards.ingest` 是怎么被驱动的？**
`Consolidator` 构造时接受一个 `onBlock(chatKey, block)` 回调，每写成一个小时块就回调一次。
`index.js` 传的是 `(chatKey, block) => cards.ingest(chatKey, block.snippets)`。
回调抛错被吞掉 —— 抽卡只是附带产物，绝不能影响巩固。
⚠️ 传进去的是**这一轮新加进来的碎片**，不是整块的碎片。块是增量合并的，
把整块重喂一遍会让同一张卡的 `hits` 每 10 分钟涨一次，排序随之失真。

**为什么 `consolidateAll` 从 `messages/` 列会话，而不是从索引列？**
因为全新安装时索引是空的。早先版本用 `store.listChatKeys()`（只知道索引里已有的会话），
结果是定时器拿到空列表、什么都不做，**插件永远不会自己启动**。
这个 bug 是端到端测试（造一个假宿主目录真的 import `index.js`）逼出来的 ——
离线自测每次都直接调 `consolidateChat(某个 chatKey)`，从来没走过"从零自举"这条路径。

**设置项为什么不能用 `clamp()` 取值？**
`clamp(undefined, lo, hi)` 返回 **lo**。于是"用户没配置"被悄悄解释成"用户配了下限"，
不抛错、只是功能静默失效。本插件真实踩过三处：
`cardIdleDays` 未配置 → 夹成 **1 天**（卡片存活一天就被 `sweep()` 清空）；
`maxCards` 未配置 → 夹成 **20 张**；`crossTurnMaxChars` 未配置 → 夹成 **80 字符**。
统一改用 `num(value, fallback, lo, hi)`：**没配就用 fallback**，配了才夹。
（`clamp` 保留给"已知有值、只需夹住"的场合，比如块权重。）

**为什么记忆强度要同步进 `state.json`？**
索引文件丢失/损坏时 `index()` 会从块文件重建倒排 —— 但块文件里**没有**
`score/hits/lastHitAt`（那三个是索引侧字段）。早先版本重建后所有块被打回
`score=1, hits=0`，正好在崩溃恢复这种最需要保住权重的时刻把权重清空。
现在 `markHit` 会顺手写进 `state.json` 的块元数据、重建时读回来；
`state.json` 的写入带 30 秒节流，不会每轮碰盘。
⚠️ v1.4.0 加了 `S`（每块稳定性）之后，**同一个坑原地又出现了一次**：
`#indexInto` 必须把 `S` 和 `passiveHits` 一起读回来，否则重建后 S 退回全局 45 天 ——
权重看着还在，衰减速度却被偷偷改回默认值，"记得牢"这件事丢了。
`rollupChat` 合并日块时同理要 `S = Math.max(...)` 继承，不然越老的块滚得越多、稳定性丢得越狠。

**`S = 0` 为什么不能交给 `num()` 处理？**
`num(value, fallback, lo, hi)` 只对 `undefined`/`null`/`''` 用 fallback。
索引重建时"没有 S 就写 0"，而 `num(0, 45, 1, 3650)` 会把 0 夹到**下限 1** ——
于是"没有稳定性"被解释成"半衰期 1 天"，老块会在两天内跌破淘汰线然后被删光。
`stabilityOf()` 必须自己判 `!Number.isFinite(raw) || raw <= 0`，让 0 与"缺失"同义。

**自动注入的冷却为什么不能在 `build()` 里记？**
`appendToLastUser` 找不到 `user` 消息时会返回 `false`（宁可不注入也不碰 system 前缀）。
如果 `build()` 自己就把冷却记掉，这一次冷却被白吃掉 —— 这条旧事被锁 30 分钟，
而模型根本没看到它。和冲突提醒的 `markAnnounced` 是同一个坑：
**一切"记账"都放在确认送达之后**。

**冷却名单为什么比"展示过的块"大？**
日块和小时块常常装着同一句话。只锁真正展示的那个块的话，下一轮另一个块换个名次上来，
会把同一件旧事**再念一遍** —— 正是冷却要防的事。所以 `build()` 返回两个名单：
`chunkIds`（真的写进提示词，只有这些记被动命中）和
`cooldownIds`（= 展示过的 + 内容被展示覆盖的，全部进冷却）。
多出来的那些**不记**被动命中，因为模型确实没看到它们。

**为什么测试里的 `synth()` 必须对齐整点？**
早先 `base = Date.now() - N 天`，分钟数与当前时刻相同：每小时 6 条从 `HH:56` 铺到 `HH+1:01`，
于是"每个小时一个块"变成"每批消息横跨两个块"，**块数随运行时刻漂移**。
块数一变 `df/n` 就变，`dfCutoffRatio = 0.7` 的剪枝就会时而剪掉「猫粮」时而留下 ——
表现为"同一份代码上午全绿、下午三条失败"。改成 `Math.floor(... / 3600000) * 3600000` 对齐整点后才稳定。

**测试里不能连打 `markHit` 来造"记得牢"的块。**
新模型的增益是间隔依赖的（`r = log2(1 + 间隔/S)`），同一瞬间连打若干次 `r ≈ 0`、几乎不加分。
要造出高权重的块只能用 `hitAged()`：先把 `lastHitAt` 往前拨若干天再命中，
等价于"上次想起是在 N 天前"。**这本身就是要钉住的行为，不是 bug。**

**日块合并为什么要继承权重？**
`rollupChat` 把一天的小时块并成日块。若日块从出厂值 `score=1, hits=0` 开始，
"某天被反复想起的那段"一合并就被打回原形 —— 越重要的记忆反而越容易被
`forgetSweep` 清掉，正好反了。现在继承 `max(score)` / `sum(hits)` / `max(lastHitAt)`。

**`noteBlock` 必须先于 `indexBlock`。**
块文件里**没有** `score/hits/lastHitAt/S`（那四个是索引侧字段，只在 `state.json` 里）。
`#indexInto` 靠读 `state` 把它们捞回来，所以顺序反了的话，刚写好的块在索引里就是
`score=1 / hits=0 / S=0`。`rollupChat` 里是正确顺序，但 `reviveBlock` 里**写反过一次**：
复活出来的块权重被清零，下一次 `forgetSweep` 会立刻把它当"低权重老块"再删一遍。
（J4 的 `hits >= 1` 断言就是钉这个的。改一处要改两处，注释里也写上了。）

**注入的时间不能用已经格式化过的字符串再 `formatWhen` 一次。**
`buildHit` 里给模型的 `snippets[].when` 是 `"MM-DD HH:MM"` 字符串。
`inject.js` 早先写成 `formatWhen(l.when)` —— `Number("10-14 08:00")` 是 `NaN`，
而 `formatWhen` 对 NaN 会回落到 `Date.now()`，于是**自动注入的旧事永远显示成刚刚发生**，
模型据此判断"这是新事"，正好把"旧事"说反了。现在 `recallForPrompt` 把原始 `ts`
一起带出来，调用方用它格式化。

**巩固为什么不只读文件末尾？**
早先版本 `loadMessages` 取最后 `batchMax` 条，配合"水位线只往前走"，结果是
**会话超过 `batchMax` 条时早期消息永远进不了记忆库**，而且不报错。
现在按 id 分页：从水位线之后取一批，取不完下一轮接着取（`state.backlog` 标记），
最终扫完整个会话。同时用 `mtime + size` 判断"文件没动过"就直接跳过读取 ——
绝大多数 tick 其实没有新消息，空转的定时器不该每 10 分钟 parse 一遍几 MB 的 JSON。
（注意 `backlog` 为真时必须继续读，"文件没变"≠"读完了" —— 这个坑是 F 组回归断言抓到的。）

**冲突检测为什么用"探针"而不是直接调 `memory.status`？**
`api.capability()` 只取第一个提供者，没法直接问"我排第几"。所以给自己的
`memory.status` 加了一个内部探针参数：如果先答话的是我，就短路返回一个引擎标记。
两个理由——① 不短路的话，我在 `activate()` 里做自检就等于把整个引擎唤醒一遍
（建实例、读索引、遍历目录算体积），热重载一次白等一次；② 短路发生在
`instance()` 之前，也就顺手避免了"自检 → 调 memory.status → 又自检"的递归。
探针只认自己的标记，宿主工具传的 `{}` 照常走全量状态（G 组有断言钉住这两点）。

**为什么自检不能放在 `setup()` 里？**
`setup()` 是模块被 import 的时候调的，那一刻本插件**还没注册进能力表**
（`manager.register()` 在 import 返回之后才跑）。这时候探针必然只看到内置版，
会把"我还没上桌"误判成"我抢不过它"，于是每次启动都误报。
检测必须放在 `activate()` —— 那时所有 Skill 都已注册完毕。

**`try/catch` 会把笔误一起吞掉。**
`ConflictGuard` 的构造函数里读冷却时间戳包了 `try/catch`（存储不可用不该拖死插件），
结果我把常量名从 `STORE_KEY` 改成 `STORAGE_KEY` 时漏改了一处 —— `ReferenceError`
被那个 `catch` 静静吃掉，表现是"冷却每次重启都重置"，**不报错、只是功能静默失效**，
跟这个插件一直在防的那类 bug 一模一样。是 G 组的"重启不重新计时"断言把它抓回来的。
教训：兜底 `catch` 里别只写注释，**给这条路径配一条断言**。

**同一个坑第二次踩到（v1.7.1）**：`buildInject` 给「自动想起旧事」段包的 `try/catch`
吞掉了 `inject.js` 里一次缺 `num` import 的 `ReferenceError` —— 用户把
`recallRowWidth` 调成非 0，每轮自动注入静默死亡，日志里只有一行 warn。
把它逼出来的是新增的 `tools/bench-tokens.mjs`：「省 token 三件套全关」那组配置
（`recallRowWidth: 90`）第一次跑就炸。**结论：实测脚本的每个配置组合都是断言，
包括那些"故意开倒车"的对照組。**

## 已知限制

- 没在真实 QQ 群里跑过。173 项断言用的是合成消息，真实消息的字段形态、多会话并发巩固、
  宿主 5 秒钩子超时下的表现都还没有实测数据。
- 与内置版**同名能力**，必须关掉一个，否则谁生效取决于加载顺序。
  插件会主动提醒你（见「冲突自检」），但它**不会替你关** —— 宿主没给插件改别的 Skill
  配置的接口，硬来就只能去改宿主的配置文件，那是这个插件从头到尾都在避免的事。
- 冲突自检的"谁抢到了能力"只能靠探针**间接**判断：探针问不出来时按较轻的 `duplicate` 报，
  宁可少说一句，也不误报成 `shadowed`。
- 私聊里那句提醒终究是"塞进提示词、指望模型转达"，不是直接给你发消息 ——
  插件没有发消息的接口（`createSkillApi` 的白名单里没有）。日志和 `memory_status`
  里那两条是确定送达的，私聊那句是尽力而为。
- 插件拿不到路由注册权，所以**不做** `/api/memory-files`（那是核心 `MemoryStore`
  的群友印象接口），本插件只负责长时记忆 + 归档。
- `dfCutoffRatio` 与 `autoRecallBudget` 建议按实际数据调一遍：默认值是按"一般群聊"定的，
  块数很少时大部分词本来就在多数块里，这时 0.7 可能剪得很凶。
- 待办 / 跨轮 / 语义卡 / 旁听这四项的抽取是**启发式正则**，不是模型判断。
  想确保某件事被记住，让模型显式调 `memory_todo`，别指望正则抽得准。
- v1.7.0 的人类记忆机制是**粗粒度近似**：共激活联想按块 id 计数而非内容相似度
  （"当时一起想到"目前等于"同一轮检索里一起出现"）；时段情境只把一天切成五段，
  没有生理学意义上的昼夜模型；睡眠重演一次最多带一块，不做序列重演。
- v1.7.1 的词清单（`terms`）让索引体积 +13%（实测），且**老索引升级后第一次巩固**
  仍会对没有 `terms` 的块走全表扫描回退（行为正确、只是慢），要等这些块被
  重新索引（汇总 / 复活）后才走上快路。
- `state.json` 仍是**单文件**（所有会话的块元数据都在里面），只是写入带节流。
  会话数上千时它会长到几百 KB —— 目前够用，但这是下一个该拆的地方。
