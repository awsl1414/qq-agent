# 项目通用规范

跨前后端都适用的长期约束。改代码、写注释、更新文档时逐条对照。

## 术语一致性

同一个概念在代码、注释、文档、界面上必须用同一个词：

| 概念 | 用词 | 不要用 |
|---|---|---|
| 加载单元统称 | 扩展 | 模块、Skill |
| 确定性型 | 插件 | — |
| LLM 型 | 技能 | Skill |

例外（保持原样）：代码标识符（`skillId`、`createSkillApi`、`skill.json`、`config.skills`）、错误原文（`Skill <id> 未声明…`）、固定术语「内置模块」（与 `builtin-modules.json` 同名）。

文档章节统一 `N. 标题` 编号；交叉引用写「第 6 节」而不写行号。注释里引用代码位置一律用符号名（`plugin-loader.js` 的 `loadSkillDir`），不写 `file.js:123`，因为行号会漂移，且已经全部漂移过一次。

## 解耦：分析是否值得，不一味拆

拆之前先问三个问题：

1. **它有没有第二个调用方？** 只有一个调用方的"提取"，是把耦合从文件内挪到文件间，净损失
2. **它有没有独立的变更理由？** 改 A 从不导致改 B，才值得分开
3. **拆完接口比实现长吗？** 如果传参和返回值比逻辑本身还多，别拆

现有解耦是**按能力名**而非按模块名（`getCapabilityProviders`），这是有价值的范例：换实现不改调用方。反例是"为了拆而拆"：`createRoutes(deps)` 已经有 23 个注入项，再加之前先确认真的需要。

## 修问题：找根因，从底层修

遇到问题时先定位**本质原因**，再动手。表面修复的代价不是"不够优雅"，而是同类问题会以另一种形态再出现一次。

一个修复是否触到根因，看它能不能回答：**为什么会发生**（不是"哪一行错了"，而是"什么条件让这一行必然出错"）、**改这里能阻止同类问题吗**（换个输入还复发就是补丁）、**别处有没有同样的模式**（一个 bug 通常是一类 bug 的样本）。

| 表面修复 | 为什么不够 | 该怎么做 |
|---|---|---|
| 加 `try/catch` 吞异常 | 异常源还在，只是不报了 | 找到抛错的源头，修正导致它抛错的状态 |
| 加 `setTimeout` 绕时序 | 竞争窗口变小但没消失 | 找出真正的时序依赖，用状态机或显式等待消除 |
| UI 层判空不显示 | 数据为什么为空没解决 | 修数据产生方，UI 只负责呈现 |
| 失败就重试 | 失败原因未消除，只提高成功率 | 先查清原因；确认是瞬态故障（网络抖动、限流）才重试 |
| `if (!x) return` 早退 | 崩溃消失，但 `x` 为空的原因还在 | 找到 `x` 该在什么时机被赋值，修赋值时机 |
| 调大超时 / 调小批量 | 阈值一变就复发 | 找出真正的耗时来源 |

**例外**：确认根因在外部（第三方 API 不稳定、协议端行为不可控）时，防御性代码是正确做法，但注释要写明**这是防御而非修复**以及防的是什么。

本项目的范例：`orchestrator.js` 的 `wake()` 把 `startingChats.add` 提到守卫之后立刻执行，因为根因是**守卫与占坑之间夹着一个真实的网络请求**。而 `prompt.js` 的方括号问题用了两层（提示词立规矩 + 发送前剥壳），这不是表面修复，因为小模型的概率性行为无法被单层消除。**判断标准是能不能说清每层在防什么，不是层数。**

## 通用编码规范

### 魔术数字

代码里直接写死的数值，读代码的人无法从上下文判断它为什么是这个值、改了会怎样。

**必须提取成具名常量**：

| 场景 | 例 |
|---|---|
| 业务阈值 | 熔断次数、重试上限、分页大小、超时、缓存 TTL |
| 容量与预算 | 字符/字节上限、并发数、批量大小 |
| 有单位含义 | 毫秒、字节、秒（名字里带上单位：`TIMEOUT_MS`、`MAX_BYTES`） |
| 同一个值出现 ≥2 次 | 任何重复字面量 |
| 与外部契约对齐 | 与后端 `MAX_UPLOAD` 对齐的上限、OpenAI 的 64 字符限制 |

**不算魔术数字，可以就地写**：

- `0` / `1` / `-1` 这类结构性取值（索引、初始值、`indexOf` 的 `-1`）
- 数组/字符串的 `length` 比较中的小整数
- 单位换算因子（`1024`、`60`）；但若它是某个上限的组成部分，整个表达式要一起具名
- 正则与格式串内部的数字
- 一次性的 UI 排版数值（padding、行高），除非多处复用

**写法要求**：

```js
// 好：名字说明了它是什么，注释说明了为什么是这个值
const SKILL_STORAGE_MAX_BYTES = 1024 * 1024;   // 1MB，超过 set 直接抛错
const MUTE_REVERIFY_MS = 15_000;               // 与协议端 60s single-flight 对齐

// 坏：读的人不知道 30000 是什么，也不知道能不能改
if (Buffer.byteLength(text) > 30000) throw new Error('too large');
```

常量名用 `SCREAMING_SNAKE_CASE`，带上单位后缀。项目里已有 70 个这样的常量（`*_MS` / `*_BYTES` / `*_SEC`），沿用这个惯例。**改一个值就要改一处**，不要在多处同步。

### 其他通用约定

- **不用魔法字符串**做状态/类型判断，用导出的常量或 `Set`（项目里 `CATEGORY_META`、`VOLATILE_SECTION_IDS` 是范例）
- **不用 `==`**，一律 `===`（`null` 判断可写 `x == null`，这是唯一例外）
- **不用 `var`**；`const` 优先，需要重赋值才用 `let`
- **不用 `arguments`**，用剩余参数
- **异步错误必须被处理**：`await` 或 `.catch()`，不要留下悬空的 Promise。项目里 `src/harness/doctor/scan.js` 会扫出未处理的 Promise
- **空 `catch` 必须写注释**说明为什么可以忽略，否则它和"漏掉错误处理"无法区分
- **不用 `console.log` 记日志**，走 `src/logger.js`（`electron/` 与少数入口除外，见各自文件头注释）
- **文件路径用 `path.join`**，不手拼字符串

## 更新日志（`CHANGELOG.md`）

### 只在升版本时压缩

`CHANGELOG.md` 顶部永远只有两类内容：**已发布版本**（按版本倒序）和**未发布**。

**升版本时的动作**：

1. 把 `## 未发布` 下的内容整块转成新版本条目，加上版本号与日期
2. **压缩**：删掉调试过程、中间尝试、被否决的方案、内部报告路径、逐轮次编号、时间戳
3. 保留：每个改动的**根因**与**用户可见的后果**

压缩的对象是"怎么发现的"，不是"改了什么"。用户需要知道这个版本修了什么、为什么之前是坏的，不需要知道排查了几轮。

**不压缩 `## 未发布`**：开发期间往里追加完整记录，方便回顾。压缩只发生在升版本那一刻。

### 写什么、不写什么

| 写 | 不写 |
|---|---|
| 用户能感知的行为变化 | 内部重构、代码风格调整 |
| 问题的根因（"只查 PATH，看不见设置页下载的"） | 排查过程（"查了三轮才发现"） |
| 影响面（"五处统一走同一条解析链"） | 涉及的文件行号 |
| 破坏性变更与升级注意事项 | 中间版本号（同一版本内不要反复升降） |

**一条版本只对应一份内容。** 历史上出过"同一个版本号对应两份不同内容"的事故（安装包停在旧构建上，作者本地已经改了），这是最坏的发布形态。升版本时确认 `package.json` 的 `version` 与 CHANGELOG 最新条目一致。

### 格式

```markdown
## 0.4.9.0 · 桌宠与壁纸进包（2026-10-24，需重启）

### 新增：桌宠
- …

### 修复
- **现象一句话**：根因 + 改法。
```

- 版本标题：`版本号 · 一句话主题（日期，是否需重启）`
- 小节用 `### 新增` / `### 变更` / `### 修复` / `### 清理`
- 每条以**加粗的现象描述**开头，后面跟根因与改法
- 需要用户动手的（重启、重装、重新配置）必须写明

## 不留兼容代码

**清理的是兼容代码，不是兼容的业务逻辑。**

| 保留 | 清理 |
|---|---|
| 用户数据迁移（`src/upgrade.js`、`config.js` 的 `migrateSnowlumaToProtocol` / `migrateLegacySkills`），因为用户磁盘上的旧数据必须能读 | 已无调用方的 shim：`tool-registry.js` 的 `isToolEnabledLegacy` |
| 旧清单格式适配（`plugin-loader.js` 的 `adaptLegacyPrompt`），因为第三方扩展仍在用 | 为已删除版本留的 fallback 分支 |
| 协议兼容（OneBot v11 不同实现的差异） | "先留着以防万一"的未使用导出、注释掉的代码 |

判定标准：**有没有真实的使用方**。没有就删，包括它的测试和注释。不确定时先 grep 全仓（含 `plugins/`、`skills/`、`tests/`），确认零引用再动手。

删除时连带清理：该导出的 `export`、指向它的注释、只为它存在的测试。`builtin-modules.json` 里已删模块的条目也要同步移除。

## 用最优方案，不用"够用"方案

选实现前先看现有代码里同类问题是怎么解的，优先复用而不是新造。新增依赖前确认标准库做不到；本项目目前只有 3 个运行时依赖（`js-yaml` / `undici` / `ws`），保持这个量级。

## 注释

注释解释**为什么**，不解释代码在做什么。写清事故成因与不可改的原因，比描述实现有用。

- 不写行号引用（会漂移），写符号名
- 同一函数不要叠多份 JSDoc，合并成一份
- 过时的注释按**实际代码**更新，不要保留与实现矛盾的描述
- 版本号、文件路径这类易失真的具体值，能删就删，删不掉就标注"当前值"而非"永远如此"

## 规则文件（`.claude/rules/`）

本项目用 Claude Code 官方机制拆分规范，按加载时机组织，不按内容长短：

| 文件 | 加载时机 |
|---|---|
| `conventions.md` | 无 `paths`，会话启动即加载 |
| `frontend.md` | 触碰 `ui/**`、`*.css`、`*.html` 时 |
| `backend.md` | 触碰 `src/`、`electron/`、`plugins/`、`skills/`、`tests/` 时 |

写规则时注意（已从 2.1.316 实现核实）：

- **frontmatter 只认 `paths` 一个键**，其它键被静默忽略
- 尾部 `/**` 会被**剥成裸目录名**（`src/**` → `src`）。要匹配目录下所有文件，写 `src/**/*`，别写 `src/**`
- `paths` 匹配的是**文件路径**，不是目录
- 用户级 `~/.claude/rules/` **不支持** `paths` 条件加载，路径规则只能放项目级
- 加新规则文件前先确认它真的需要独立加载时机；能并入现有文件就不要新增
