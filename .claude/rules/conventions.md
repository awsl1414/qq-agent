# 项目通用规范

适用于代码、注释和文档。领域契约见前端、后端规则。

## 1. 项目核心原则

- **采用最佳方案**：以正确性、安全性、架构契合度、性能和长期维护成本综合判断。存在实质性取舍时比较可行方案并说明依据；不以“能跑”“改动最少”或“沿用旧写法”代替方案判断，也不为追求形式上的先进增加无收益的复杂度。
- **从根本分析修复问题**：沿输入、状态变化、调用链和责任边界追查成因，在产生错误的源头或负责契约的位置修复，并检查同类路径；验证原触发条件及相关边界，不能只让表面现象消失。
- **代码与文档高度统一**：同一概念、接口、配置、默认值和行为在代码、测试、注释、开发文档与用户界面中保持一致。行为或契约变更时，同次更新受影响内容，清理过时描述；发现实现与文档冲突时，核实预期契约后统一修正。
- **遵循明确的技术基线**：本项目以原生 JavaScript、Node ESM、浏览器原生 DOM / CSS 和 Node 内置测试工具为基础，具体写法按第 4.2 节及前后端规则执行。采用新能力时核实最低运行版本是否支持，并在同一职责范围统一实现；不能由各文件自行选择另一套框架、模块体系或工具链。
- **主动清查并清理兼容代码**：每次修改相关链路时，检查历史 shim、旧接口转发、重复适配和失效 fallback；确认已无真实使用方后连同专属测试、导出与过时文档一起删除。清理对象是历史技术实现遗留的兼容代码，不是仍需支持的兼容业务逻辑；用户数据迁移、第三方扩展契约和协议实现差异按第 3 节判断。

## 2. 根因修复与实际边界

- 修问题前先定位触发条件、错误状态的来源和同类模式，再在负责该状态或契约的位置修复。
- 不用吞异常、延时、判空早退、调阈值或盲目重试掩盖根因。只有确认是可恢复的瞬态故障时才重试，并明确次数、停止条件与副作用。
- 根据真实输入来源、调用契约和运行环境确定防御边界。外部输入在进入系统的边界校验；内部沿用明确契约，不逐层重复判空、校验或添加 fallback。
- 新增兜底须能说明具体失败场景、该层的处理责任和失败后的可观察结果。契约被破坏时保留可定位的错误，不用默认值伪装成功。
- 第三方 API、协议端和模型输出存在真实不确定性时，在负责该边界的位置处理，并用注释说明防的是什么。多层防御只有在各层承担不同责任时才保留；安全边界的独立校验不能以去重为由删掉。

## 3. 复用、解耦与兼容

先查现有同类实现，评估是否符合核心原则后优先复用；需要改进时统一相关实现，避免并存两套契约。新增依赖前确认标准库和现有依赖是否能合理解决，不为假设中的需求增加抽象。

拆分前确认是否有独立职责或变更理由、真实复用需求，以及拆分后接口是否比原实现更复杂。单一调用方不自动构成拆分理由，也不排除有明确职责边界的拆分。

兼容逻辑按真实使用方判断：

- 修改前检索受影响链路中的兼容分支，交付前复查是否新增或遗留了已无必要的适配层；检查范围覆盖调用方、注册入口、配置、测试和文档，不仅检查当前文件。
- 保留仍有使用方的用户数据迁移、第三方扩展格式适配和协议实现差异处理。
- 清理已无使用方的 shim、旧版本 fallback、未使用导出和注释掉的代码，不保留“以防万一”的分支。
- 删除前全仓检索调用、动态注册和外部契约，不能只凭内部零引用判断公共接口无用。
- 清理限定在本次改动相关范围，并同步清理导出、过时注释和专属测试；内置扩展删除后同步更新指纹基线。

## 4. 编码约定

- `const` 优先，需要重赋值才用 `let`；不用 `var`、`arguments`。
- 使用 `===`；仅同时判断 null / undefined 时允许 `x == null`。
- 状态、类型等契约值复用已有常量或集合，不在多处散落魔法字符串。
- 异步操作必须 `await` 或明确处理拒绝；空 `catch` 须说明为什么可以忽略。
- 核心日志使用 `src/logger.js`，扩展使用注入的日志接口；Electron 与入口文件沿用其现有日志约定，不新增随意的 `console.log`。
- Node 文件系统路径用 `path.join` 等路径 API；URL 和浏览器资源路径遵守对应 URL 契约。

### 4.1 数值与常量

业务阈值、容量预算、超时、缓存 TTL 和外部契约上限必须具名；同一语义的重复数值共用常量。常量用 `SCREAMING_SNAKE_CASE`，有单位时带 `_MS`、`_BYTES`、`_SEC` 等后缀，必要时注释说明取值依据。

结构性 `0` / `1` / `-1`、长度比较中的小整数、单位换算因子、正则或格式串内部数字、一次性 UI 排版数值可以就地写；构成业务上限或被同一语义复用时仍须具名。不同语义恰好相等的数字不强行合并。

### 4.2 技术基线与统一写法

| 场景 | 本项目采用的具体约定 |
|---|---|
| 依赖与运行环境 | 用 `package.json` 的 `engines` 确定最低支持版本，`packageManager` 确定 pnpm 版本，`pnpm-lock.yaml` 锁定依赖；不生成其他包管理器的锁文件。共享后端代码同时满足 headless Node 与 Electron 主进程环境。 |
| Node 模块 | 使用原生 JavaScript ESM 的 `import` / `export`；相对导入写完整文件扩展名，内置模块写 `node:` 前缀，如 `node:fs`、`node:path`。工具明确要求 CommonJS 的入口按其契约保留，不扩散到业务代码。浏览器脚本遵守前端规则中的普通脚本 / ESM 桥边界。 |
| URL 与默认值 | URL 解析和查询参数使用 `URL` / `URLSearchParams`；文件路径使用 Node 路径 API。只在 null / undefined 时取默认值用 `??`，不以 `||` 吞掉合法的 `0`、`false` 或空字符串；业务确需将空值视为缺失时明确判断。 |
| 异步与取消 | Promise 接口使用 `async` / `await`；调用支持取消的 API 时透传 `AbortSignal`，主动取消使用 `AbortController`。超时先复用现有请求封装；需要新增取消机制时集中在负责请求生命周期的封装中，不在每个调用点叠加定时器，也不把 `Promise.race` 当作底层任务已取消。 |
| 测试 | 沿用 `tests/*.test.mjs`、`node:test` 与 `node:assert/strict`，通过已有 pnpm 脚本或 `node --test` 执行。修复测试验证触发条件与可观察行为，不为同类测试再引入另一套框架。 |

本表是项目选定的约定，语言与模块语义查 [Node ESM 文档](https://nodejs.org/api/esm.html)。查阅 API 时核对其引入版本，不能把最新版文档中的所有 API 都视为最低支持版本可用。技术栈调整须同时更新受影响的实现、依赖声明、验证入口和规则，不能只在局部另起一套。

## 5. 术语、注释与文档

| 概念 | 统一用词 |
|---|---|
| 插件与技能的统称 | 扩展 |
| 确定性型扩展 | 插件 |
| LLM 型扩展 | 技能 |

代码标识符（如 `skillId`、`skill.json`）、错误原文和固定术语“内置模块”保留原样；不把所有代码模块都改称扩展。

- 文档章节用 `N. 标题` 编号；交叉引用用章节或符号名，不用易漂移的行号。
- 注释解释原因、契约与取舍；同一函数合并为一份 JSDoc，过时注释按实际实现更新。
- 版本、文件数量、引用次数和阈值优先指向权威声明，不在规则中复制易失真的快照。
- README 面向使用者，开发契约放开发文档，临时任务记录不混入长期规则。

## 6. 更新日志与版本

### 6.1 开发期间

用户可感知的变更追加到 `CHANGELOG.md` 的 `## 未发布`，记录现象、根因、最终行为和影响范围。开发期间不压缩已有未发布记录；排查过程、中间方案、内部报告路径、纯重构和代码风格调整不写入用户日志。

### 6.2 升版本

1. 更新 `VERSION`，同步 `package.json` 的 `version` 与 CHANGELOG 版本标题。
2. 将 `## 未发布` 内容转为新版本条目，按上一个已发布版本到本次最终实现的差异压缩；保留根因与用户可见后果，去掉内部过程和重复项。
3. 不把同轮开发中引入又修掉、用户从未遇到的问题写成已发布缺陷；“新增”“不再”等描述必须符合已发布版本的实际行为。
4. 运行 `pnpm run verify:version`。已发布版本号不能对应两份不同的发布内容。

版本倒序排列。标题使用 `版本号 · 一句话主题（日期，需重启等操作要求）`；小节用 `新增` / `变更` / `修复` / `清理`；条目以加粗的现象描述开头，接根因与改法。重启、重装、重新配置等用户操作须写明。

## 7. 规则维护

- 入口文件提供导航，通用规则只放本文件，领域规则分别放前端、后端文件；同一约束维护一份正文，其他位置引用。
- 新规则优先并入职责相符的现有文件；只有需要独立适用范围时才拆文件。
- 路径规则使用 `paths` frontmatter，匹配文件路径；目录下所有文件写 `目录/**/*`。
- 规则加载机制由根目录 `AGENTS.md` 维护，不在多处复制加载顺序或工具实现细节。
