# 前端规范

## 1. 实际运行环境

`ui/` 为原生 HTML / CSS / JS，不使用前端框架。控制台既用于 Electron，也由 `pnpm run server` 提供给浏览器；桌宠等独立窗口另有 Electron 专属能力。

- 桌面运行时版本以 `package.json` 和锁文件为准，不在规则中固定 Chromium / Node 的对应版本。
- 通用控制台改动同时考虑桌面与 headless 访问；Electron 专属能力遵守现有桥接与可用性判断。
- 新增 Web 特性核对 MDN Browser Compatibility Data 与 Baseline；通用控制台默认采用 Baseline Widely available 的能力，并验证 Electron 与当前主流浏览器。仅在 Electron 独立窗口使用的能力按其运行时核实，不据此提高通用控制台的要求。
- 复用下述原生实现与公共封装；遇到旧写法时按对应职责统一改进，不并存两套实现。新增框架、预处理器或构建步骤属于技术栈调整，按通用规则第 4.2 节处理。

## 2. 脚本加载契约

- Node 模块写法见通用规则第 4.2 节；浏览器脚本以 HTML 中的实际声明为准，不能因 `package.json` 的 `type: module` 就把普通脚本当作 ESM。
- `ui/index.html` 通过 `defer` 按序加载 `ui/app/*.js` 普通脚本，跨脚本共享顶层绑定；这些文件不能直接添加 `import` / `export`。
- `ui/app.js` 是 ESM 桥，将所需 `/vendor/*.js` 导出挂到 `window`；其他页面和入口按各自 `<script>` 声明处理。
- 新增或删除渲染脚本时，检查 `ui/index.html` 的引用、执行依赖，以及 `ui/app.js` 和文件头说明；涉及桥接时同步修改桥，不因脚本数量变化而添加空改动。

### 2.1 DOM 与请求接口

- 控制台业务请求复用 `ui/app/00-core.js` 的 `api()`，沿用认证、错误文案与超时参数；启动探活、流式响应等不同契约使用其已有专用路径，不为普通业务请求另建 `fetch` 包装。
- 纯文本写入用 `textContent`；HTML 模板中的外部文本用现有 `esc()` 转义。URL 单独校验协议和目标，HTML 转义不能代替 URL 校验。事件用 `addEventListener`，不新增内联事件属性。

## 3. 样式与交互

样式集中在 `ui/style.css`，设计令牌定义在 `:root` 与亮暗主题选择器中。

### 3.1 组件编辑入口

- 复用 `.sl-*`、`.btn`、`.field`、`.skill-*` 等现有外壳与控件；页面专属规则使用页面前缀，避免单页调整污染通用组件。
- 修改组件前先用 `rg` 全文搜索选择器及其状态、变体，确认出现次数、所在条件和覆盖顺序；不能只改首个匹配，否则后续规则可能覆盖修改。
- 一个组件只能有一个权威状态组，默认 / hover / active / disabled / focus 集中维护；禁止把同一属性分摊到「基础定义 + 换肤覆盖 + 页面修补」。跨区域覆盖属于历史遗留，新代码不得新增。收敛已有组件时先记录各主题、状态和响应式条件下的最终值，再迁入同一区域并删除旧位置的对应规则；保留必要的条件分支，不按重复次数直接合并。
- 新增按钮变体必须在定义旁说明与 `.btn` / `.btn-primary` 的继承关系、复用状态和覆盖属性，不得靠更高特异性另起一套；修改通用 hover 时同时检查主按钮和页面变体，防止继承到意外的背景或缩放。
- HTML 优先使用语义元素和原生表单控件；开关沿用 `input.sw`（40×22 轨道），布局保持开关在左、文字在右，不混用方块复选框。
- 表单控件提供关联的 `label`，图标按钮提供可访问名称；保留原生键盘操作，不用可点击的 `div` 代替按钮。
- CSS 能直接表达的状态优先用选择器（如 `:has()`），需要业务状态时才使用 JS，避免 DOM 与额外状态不同步。
- 常规布局优先使用 Flexbox / Grid；界面主题的透明与混色沿用 `color-mix(in srgb, var(--令牌) 比例, transparent)`，由 CSS 自定义属性控制，不另写 JS 逐元素设色。壁纸取色等业务算法沿用其专用实现，不受此主题样式规则限制。
- 状态条用于异常或需要用户行动的状态，正常时不重复已有信息。

### 3.2 主题与颜色令牌

- 主页面主题属性写在 `document.documentElement`；主题选择器必须匹配 `html` 或 `:root`，禁止 `body[data-theme=...]`。主页面 body 没有该属性，写在 body 上会静默失效。
- 首屏脚本 `ui/theme-boot.js` 与初始化使用的 `getThemePref()` 必须采用同一默认主题决策，不能各自选择默认值；改默认策略时同步验证无存储、显式明暗、system 和 `?`，防止启动前后主题跳变。本地偏好与后端配置的首次同步也须明确优先级。
- 颜色消费使用令牌，不硬编码色值；令牌定义中的色值和 `var()` 的备用色不属于绕过令牌。
- 新增颜色先查语义令牌；相同角色复用已有令牌，品牌色、特效色、图表色、活跃度渐变和平台交互色（如窗口关闭红）使用独立命名令牌，不套用 `--accent` 或语义绿 / 红，以免用户强调色或状态配色改变信息含义。
- 变量定义与消费必须成对，核对名字、作用域和所属 document；定义后无人使用，或消费的令牌从未定义、始终走 fallback，均为缺陷。JS 写入、局部定义也属于生产端，不能仅凭静态 CSS 缺少定义判错；widget 的定义不能供主窗口使用。
- 修改颜色须验证亮暗主题；涉及 `?`、玻璃或壁纸取色时同时验证对应模式，避免同一组件在静态与动态路径使用不同来源。
- 修改壁纸取色或手选强调色的变量时，必须明确二者优先级，并同时核对 CSS 消费、JS 注入与 inline style 写入；只改变量名可能仍被内联值覆盖，或把强调色误映射成全局边框色。

### 3.3 令牌清理

- 删除变量沿用通用规则第 3 节的兼容代码判定，并补查 CSS `var()`、JS `getComputedStyle` 读取、内联 `style` 写入、模板字符串及注入样式、widget / 桌宠等独立 document，以及扩展的公开样式接口；只查 `var()` 会漏掉 JS 契约。
- `--radius` 是动态样式消费的反例：静态 CSS 零引用不能作为删除依据；变量别名也须追到最终消费者，避免断开仍在使用的链路。

### 3.4 间距与密度

- 默认间距阶梯为 4 / 8 / 12 / 16 / 24px；新代码优先使用对应的 `--space-*` 令牌。需要的档位尚未定义时补充定义并实际消费，不引用不存在的名字，也不另造近似数值。
- small / mini 按钮、导航、图标槽对齐可使用非阶梯值，但必须有原型或尺寸对齐依据，并在定义旁注释写出算式，例如 `12px padding + 11px 箭头 + 8px gap = 31px`；只写「视觉微调」不能解释数值来源。
- 同一组件、同一密度档的纵向间隔和横向留白分别保持一致；不同角色需要差异时注明用途，不允许同一区域无说明地混用 11 / 13 / 9px。调整后检查窄屏、文本换行和图标对齐。

### 3.5 动效、焦点与 `!important`

- 常规动效按正常样式定义，复用现有 `--dur-*` / `--ease-*`，并在 `prefers-reduced-motion: reduce` 下关闭或减弱。不能把常规动效只写在 reduce 分支，否则要求减弱动效的用户反而收到动画。
- 交互元素须有可见的 `:focus-visible`；禁止 blanket `outline: none`，除非同一条规则提供可见的替代焦点样式。用键盘检查焦点位置。
- 新增 `!important` 前先确认能否通过明确状态选择器、调整特异性或源顺序解决；不得违反组件唯一入口和按钮继承规则。`!important` 只允许用于全局可访问性兜底（reduced-motion）、`[hidden]` 显隐契约、与 JS 写入的 inline style 争夺，且必须就近注释说明防的是什么，否则后续无法判断是否可移除。
- 关键帧内禁止 `!important`，CSS 规范会忽略该声明，写入的起始值不会因此生效。
- 不得用带 `!important` 的简写属性覆盖全局 reduced-motion 兜底；例如 `transition: ... !important` 会重置 duration。修改组件过渡后检查 reduce 下的 computed style，确认时长确实关闭或缩短。

### 3.6 文件组织与覆盖来源

- 是否拆分按通用规则第 3 节的解耦判断；拆 `ui/style.css` 时先按连续段拆分，必须保持声明源顺序及加载顺序，以解析后的规则顺序和代表页面外观对照验收。拆分本身不能消除覆盖链，也不能据此承诺性能提升。
- 主题覆盖层的加载位置是行为的一部分；移动前记录并验证暗 / 亮 / `?`、组件状态及窄屏表现，移动后对照最终样式。不能直接把主题层放到最后；后置的 `desktop-pet-panel.css` 也要保持原有优先关系。
- JS 注入样式（玻璃层、壁纸取色等）与静态 CSS 是两套来源；新增覆盖前在两处确认目标属性及生效顺序，并核对 inline style，否则只看样式文件会漏掉实际胜出的声明。
- 拆分不引入 `@layer`、预处理器或构建步骤；这些属于技术栈调整，按第 1 节处理。
- 编辑 CSS 注释或搬动规则后检查注释闭合与相邻选择器能否解析，避免残留正文吞掉下一条规则。

### 3.7 不要做

1. 不机械合并重复选择器：`ui/style.css` 依赖「布局层→换肤层」顺序，重复也可能来自媒体查询或状态分支，不能按统计结果直接删除。
2. 不把所有颜色统一替换成 accent / 语义色：特效色、平台色、活跃度渐变有独立含义，fallback 不等于正常运行时硬编码。
3. 不把非阶梯间距全部四舍五入：原型、图标槽与文字对齐可能依赖这些值，先处理同组件内无依据的差异。
4. 不追求 `!important` 归零：可访问性、显隐和 inline style 有真实约束；历史用途须逐项验证后处理，不能按数量删除，新规则仍须满足第 3.5 节。
5. 不凭 CSS 内零引用删令牌：按第 3.3 节核对 JS 读写、动态样式和独立 document，避免误删 `--radius` 一类接口。
6. 不把透明窗口的零阴影改成 `none`：令牌会参与多值 `box-shadow` 拼接，`none` 与其他阴影混用会使整条值失效，须保留合法的透明零阴影。
7. 不借拆文件引入新框架、自动重命名类或一次性套 `@layer`：这些会扩大迁移范围或改变级联结果，应与保序拆分分开评审。
8. 未做首帧录像与实际前景 / 背景对比度测量，不宣称「已消除闪烁」或「所有颜色可访问」：源码路径正确不等于完成视觉验证。

相关原生能力的语义与兼容性见 MDN 的 [color-mix()](https://developer.mozilla.org/en-US/docs/Web/CSS/color_value/color-mix) 与 [:focus-visible](https://developer.mozilla.org/en-US/docs/Web/CSS/:focus-visible)；项目采用方式以上述规则为准。

## 4. 插件面板

插件面板在同源 iframe 中运行，CSP 由 `src/skills/panel.js` 的 `panelCsp()` 统一管理：

- 脚本来自允许的同源资源，不使用内联 `<script>` 或 `onclick=`；不放宽 CSP 来迁就实现。
- 样式可用 `<style>` 与内联 `style=`。
- 保留 `frame-ancestors 'self'`，使控制台可嵌入面板。
- 存储数据通道用相对路径 `../@data/storage.json`，不硬编码扩展 id。

修改面板前查阅 `doc/extend_development/panel-ui-contract.md`。修改内置插件面板文件也须按后端规则更新指纹。
